## 3. ① 계산 단계별 계측 — 구현 방식을 바꿨 이유

당초 설계는 `_parts` 4개 파일(part01·03·04·06)을 직접 수정해 `prog()` 호출부 16곳에 라벨을 박는 안이었다.
패치·검증까지 끝냈으나 **푸시 단계에서 방식을 변경**했다.

**이유**: 대용량 파트 4개(각 38KB)를 도구로 왕복시키면 한글 전사 오류 위험이 크다
(8/7·8/11 오전에 이미 2차례 발생 — `닫힐고`, `숫폼`). 바꿔야 하는 바이트를 최소화하는 구조가 더 안전하다.

**최종 구조**: `public/calc-instr.js` 한 파일로 분리. head에 `<script defer>`로 로드되어
본체 인라인 스크립트가 전부 실행된 뒤 전역 `prog()`·`track()`을 감싼다.
**계산기 본체 코드는 한 글자도 안 건드렸다.**

기대 동작은 동일하고, 대신 **트레이드오프가 생겼다**:
단계 이름이 `prog()` 호출 순서에 의존한다. flow()에 `prog()`를 끼워 넣으면 그 뒤 번호가 밀린다.
→ `calc-instr.js` 상단에 경고를 명시했고, 매핑에 없는 번호는 `qN`으로 떨어져 계측 자체는 안 깨진다.

### 심은 이벤트

- `calc_step` — `step_no`(1~16), `step_id`(`01_address` … `16_other_house_acq`)
- `calc_abandon` — `last_step_no`, `last_step_id`. 페이지 이탈 시 1회만 전송

### 발견한 기존 버그 (미수정, 기록만)

**`startBtn` 재클릭 시 본체 `pCount`가 리셋되지 않는다.**
재시작하면 진행률 바가 이어서 올라간다. 실제로는 `resetAll()`이 풀 리로드를 하고
startBtn은 랜딩 화면에만 있어 노출도가 낮다. 계측은 이 버그에 의존하지 않도록
**자체 카운터를 두고 `start_calc`에서 0으로 리셋**하는 구조로 만들었다.

## 9. 재사용 기술 노트

1. **대용량 `_parts` 수정은 변경 파일 수를 줄이는 구조를 먼저 찾을 것.**
   본체 JS를 건드려야 할 때, 외부 파일을 `<script defer>`로 붙여 전역 함수를
   감싸는 방식이 먹힐 때가 많다. classic script끼리는 전역 렉시컬 스코프를 공유하므로
   `let`·`function` 선언에 다 접근·재할당된다.
2. **`push_files`는 파일을 빼먹어도 오류를 안 낸다.** 오늘 part01을 누락한 채 체크섬만
   올라갔다. **푸시 직전에 변경 파일 목록을 `git status --porcelain`과 대조할 것.**
3. **`_parts/index.sha256`이 안전장치로 실제 작동했다.** 불완전 푸시가 배포되지 않았다.
   체크섬을 먼저 올리는 순서가 오히려 안전하다 — 맞지 않으면 빌드가 멈췄다.
4. **컨테이너 네트워크가 sekkomi.com을 403으로 막는다.** 라이브 검증은 curl로 안 된다.
   대안: Netlify MCP `get-deploy`로 `state`·`commit_ref`·`published_at` 확인, 또는 GTM 미리보기 화면의 페이지 제목.
5. **네틀리페이 배포 조회는 `get-deploy`(deployId만)를 쓸 것.** `get-deploy-for-site`에
   커밋 SHA를 넣으면 404다. deployId는 `get-project`의 `currentDeploy`에서 나온다.
6. **GTM 미리보기는 이벤트 발화와 값 전달을 분리해 볼 것.** 이벤트 목록에 떴다고 끝이 아니다.
   `변수` 탭에서 실제 값까지 봐야 "동작 확인"이다. (오늘 매개변수 1개가 빈 칸으로 저장돼 있었다)
