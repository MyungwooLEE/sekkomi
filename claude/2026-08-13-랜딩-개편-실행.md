## 3. 구현 방식 변경 (중요)

당초 설계는 `_parts/index.html.part02`를 직접 수정하는 것이었다. 로컬 검증까지 끝냈으나
푸시 직전에 방식을 바꿔다.

**이유**: part02는 40KB가 넘고 한글 비중이 높다. 자동화 도구로 통째 재업로드하면 전사 오류가 난다.
이번 세션에서만 여러 차례 실증됐다(3-1 참고).

**최종 구조**: 본체 조각 무변경. 조립된 결과물에 빌드 시점 주입.
`build-blog-featured.cjs`가 이미 쓰는 패턴이다.

- `_parts/landing-below.html` — 섹션 원본 (26KB, 미배포 경로)
- `_parts/blog-banner.html` — 배너 원본 (1.5KB)
- `scripts/build-landing.cjs` — **순수 ASCII**. 한글 앵커 대신 들여쓰기 기반 정규식으로 `.lp-foot` 매칭

### 3-1. 전사 오류 실측 (이 세션의 가장 중요한 발견)

| 대상 | 크기 | 결과 |
|---|---|---|
| `build-landing.cjs` 1차 시도 | 5.6KB | 한글 깨짐으로 푸시 자체가 스키마 오류 |
| `landing-below.html` | 26KB | 성공. CSS·JS **주석 2곳** 오타 |
| 이 기록 문서 1차 | 14KB | 성공. 본문 **10곳** 오타 |
| `netlify.toml`·`.gitignore`·`_parts/README.md`·`blog-banner.html`·`build-landing.cjs`(ASCII판) | 각 1~4KB | **전부 바이트 일치** |

**결론: 한글 밀도와 분량에 비례해 오류가 난다. 작게 쪼개고, 스크립트는 ASCII로 쓰고,
푸시 후 반드시 새 clone으로 sha256 대조할 것.**

`landing-below.html`의 주석 오타 2곳은 그대로 두었다. 본문·CSS·JS·JSON-LD는 바이트 일치라
영향이 0이고, 26KB 재푸시는 새 오타를 만들 확률이 더 높다. 다음에 이 파일을 손댈 때 같이 고친다.

## 5. 레포 전수 점검

### 발견 ① 색인 가능한 홈 중복본 2개 — 조치함

`public/` 안에 초기 수동 업로드 잔재가 남아 있었다.

| 경로 | 내용 | 위험 |
|---|---|---|
| `public/sekkomi_calc_update/` | 계산기 전체 사본 222KB | canonical 없음 · robots 메타 없음 |
| `public/sekkomi_deploy_with_logo/` | 계산기 사본 + 블로그 사본 | 계산기 사본에 canonical 없음 |

`robots.txt`는 `Allow: /`다. 즉 홈과 같은 키워드로 색인될 수 있는 중복 페이지가 2개 있었고,
하필 이번에 강화한 그 홈과 경쟁하는 구조였다. 커밋 이력상 `Add files via upload`로 초기에
올라온 뒤 방치도 있었다.

**조치**: `netlify.toml`에 `force = true` 301 리다이렉트 3건.
`force`라 정적 파일보다 먼저 평가되어 서빙되지 않고, 301이라 누적 신호는 정본으로 넘어간다.
블로그 사본은 `/blog/:splat`으로 대응시켰다.

**남은 것**: 파일 자체는 레포에 있다(26개, 860KB). 도구가 파일 단위 삭제만 지원해 호출이 26회
필요하다. 서빙은 차단됐으므로 SEO 목적은 달성됐고, 물리 삭제는 GitHub 웹 UI가 빠르다.

### 발견 ② 커밋된 `public/index.html`이 낡은 폴백 — 문서화함

레포의 `public/index.html`은 8/11 이전 버전이다(옛 title, calc-instr·JSON-LD·랜딩 섹션 없음).
빌드가 매번 덮어쓰므로 운영에는 문제가 없으나 두 가지 위험이 있다.

1. 그 파일을 읽고 현재 사이트 상태를 판단하면 틀린 결론이 나온다
2. 조립 단계는 `if [ -f _parts/index.sha256 ]` 조건부다. 조각이나 체크섬이 사라지면
   이 낡은 파일이 배포되어 **사이트가 조용히 8/11 이전으로 되돌아간다**

`_parts/README.md`에 경고와 확인 절차(`cat _parts/index.html.part* > /tmp/now.html`)를 명시했다.

### 발견 ③ `.gitignore` 부재 — 조치함

`public/rss.xml`·`public/build-index.sha256`이 빌드 생성물인데 무시 규칙이 없었다. 신설.
`public/index.html`·`public/llms.txt`는 이미 추적 중이라 제외했다 — 추적을 끊으면 발견 ②의
폴백이 사라져 더 위험하다.

### 발견 ④ 운영 규칙의 미결 2건이 실제로는 해소됨 — 확인만

- **`.github/workflows/render-reel.yml` 설치** — 파일이 레포에 있고 큐 8건 전부 렌더 완료
  (`public/reels/`에 mp4 8개 + 커버·OG 대응). 미설치 상태가 아니다
- **네이버 서치어드바이저 등록** — `index.html.part01`에 `naver-site-verification` 메타 존재

### 이상 없음으로 확인

- 블로그 글 52편 ↔ 사이트맵 53항목 — 누락 0, 유령 URL 0
- 고아 페이지 0 · 내부 `/blog/` 링크 깨짐 0 (오늘 추가한 관련글 3건 포함 실재 확인)

## 7. 운영 규칙에 반영할 항목 (본문 미수정)

`claude/세꼼이-운영-규칙.md`는 32KB이고 한글 밀도가 높다. 3-1의 오류율을 감안하면
**운영 규칙 본문에 전사 오류가 들어가면 자동화가 잘못된 규칙을 읽는다.** 그래서 건드리지 않았다.
기술 규칙은 `_parts/README.md`에 넣었다(작고, `_parts`를 만지는 세션이 반드시 읽는 위치).

1. **빌드 파이프라인** — `cat _parts` 조립 → `build-blog-featured` → `build-seo-meta` →
   `build-llms-txt` → `build-rss` → `build-landing`. 마지막이 8/13 신설
2. **랜딩 하단 수정 위치는 `_parts/landing-below.html`** — `index.html.part*`도 `public/index.html`도 아니다
3. **`.lp-foot` 동기화 주의** — `build-landing.cjs`가 히어로 안 푸터를 들어내고
   `landing-below.html` 끝 푸터로 대체한다. 한쪽만 고치면 푸터가 사라지거나 중복된다
4. **주입 단계에는 체크섬 검증이 없다** — 앵커를 못 찾으면 조용히 통과한다.
   본체 랜딩 마크업을 고쳤다면 배포 후 실제 페이지에서 섹션 존재를 확인할 것
5. **미결 2건 해소** — 5절 발견 ④
6. **대용량 한글 파일 푸시 원칙** — 3-1의 결론
