## 1. 배경 — 왜 랜딩을 손덨나

8/11에 계산기 홈의 `<title>`을 "양도세 계산기 —"로 바꾸고 JSON-LD를 심었다. 그건 **절반**이었다.

구글은 title만 보고 순위를 매기지 않는다. 본문에 그 주제를 다룰 내용이 실제로 있어야 한다.
개편 전 랜딩 본문은 히어로 카피를 다 합쳤 **약 60단어**였다. title은 "양도세 계산기"라고 하는데
그걸 뜻받침할 텍스트가 페이지에 없는 상태였다.

8/4 진단 수치가 이 문제를 그대로 보여준다 — 2주간 검색 노출이 **블로그 45편 365회 vs 계산기 홈 2회**.
순위 자체는 나쁘지 않다("양도세 계산기" 8위, "양도소득세 계산기" 12위). 다만 그 자리에 잡히는 게
`blog/yangdose-gyesangi`, 즉 **계산기를 설명하는 글**이다. 도구를 찾는 사람에게 도구에 대한 글을 보여주고
한 번 더 클릭하게 만드는 구조였다.

**이건 글을 더 써서 우회할 수 있는 문제가 아니다.** 블로그를 60편으로 늘려도 노출은 계속 블로그로 간다.
계산기 홈의 노출은 계산기 홈을 고쳐야만 늘어난다.

## 3. 구현 방식을 바꾸 이유 (중요)

당초 설계는 `_parts/index.html.part02`(랜딩 마크업 보유)를 직접 수정하는 것이었다.
로컬 패치·검증까지 끝냈으나 **푸시 직전에 방식을 바꿔다.**

**이유**: part02는 40KB가 넘고 한글 비중이 높다. 자동화 도구로 통째 재업로드하면 전사 오류가 난다.
이번 세션에서만 2회 실증됐다 —
① 첫 시도에서 `build-landing.cjs` 본문의 한글이 깨져 푸시 자체가 스키마 오류로 실패
② 26KB `landing-below.html`은 푸시에 성공했으나 주석 2곳에 오타

**최종 구조**: 본체 조각 무변경. 조립 완료된 결과물에 빌드 시점 주입.
`scripts/build-blog-featured.cjs`가 이미 쓰는 패턴이라 레포 관례와도 맞는다.

- `_parts/landing-below.html` — 섹션 원본 (26KB, 미배포 경로)
- `_parts/blog-banner.html` — 배너 원본 (1.5KB)
- `scripts/build-landing.cjs` — **순수 ASCII로 작성**해 전사 위험을 구조적으로 제거.
  한글 앵커 대신 들여쓰기 기반 정규식으로 `.lp-foot`를 매칭한다.

### 미해결 (경미)

`landing-below.html`의 CSS·JS **주석 2곳 오타**는 그대로 남겼다.
CSS·HTML·JS·JSON-LD 본문은 전부 바이트 일치라 사용자·검색엔진에 영향이 0이다.
26KB 재푸시는 **새 오타를 만들 확률이 더 높아** 기대값이 음수라고 판단했다.
다음에 이 파일을 손댈 때 같이 고칠 것.

### PC 와이드

`show()` 함수를 고치지 않고 CSS만으로 처리했다.

```css
@media(min-width:1024px){
  #frame:has(#s01.on){max-width:none;box-shadow:none}
}
```

`.screen.on` 클래스가 이미 화면 전환을 표현하므로 `:has()`로 잡으면 된다.
계산을 시작하면 `s01`이 `.on`을 잃어 **계산기는 420px로 자동 복귀**한다. 모바일은 미디어쿼리 밖이라 무변경.

## 5. 레포 전수 점검 (같은 세션)

### 발견 ①: 색인 가능한 홈 중복본 2개 — **조치함**

`public/` 안에 초기 수동 업로드 잔재 폴더가 남아 있었다.

| 경로 | 내용 | 위험 |
|---|---|---|
| `public/sekkomi_calc_update/` | 계산기 전체 사본 (222KB) | **canonical 없음, robots 메타 없음** |
| `public/sekkomi_deploy_with_logo/` | 계산기 사본 + 블로그 사본 | 계산기 사본에 canonical 없음 |

`robots.txt`는 `Allow: /`다. 즉 **홈과 똑같은 키워드로 색인될 수 있는 중복 페이지가 2개** 떠 있었다.
하필 이번에 title·JSON-LD를 강화한 그 홈과 경쟁하는 구조다.
(블로그 사본은 canonical이 정본을 가리키고 있어 상대적으로 덜 해롭지만 크롤 예산은 낭비했다.)

커밋 이력상 `Add files via upload`로 초기에 한 번 올라온 뒤 손댈 적이 없다.

**조치**: `netlify.toml`에 `force = true` 301 리다이렉트 3건 추가.
`force`라 정적 파일보다 먼저 평가되어 실제로 서빙되지 않고, 301이라 누적 신호는 정본으로 넘어간다.
블로그 사본은 `/blog/:splat`으로 정확히 대응시켰다.

**남은 것**: 파일 자체는 아직 레포에 있다(26개, 860KB). 도구가 파일 단위 삭제만 지원해
호출이 26회 필요하다. 서빙은 이미 차단됐으므로 SEO 목적은 달성됐고, 물리 삭제는
GitHub 웹 UI에서 폴더째 지우는 게 가장 빠르다.

### 발견 ②: 커밋된 `public/index.html`이 낡은 폴백 — **문서화함**

레포에 커밋된 `public/index.html`은 **8/11 이전 버전**이다(옛 title, calc-instr·JSON-LD·랜딩 섹션 전부 없음).
빌드가 매번 덮어쓰므로 운영에는 문제가 없다. 다만 두 가지 위험이 있다.

1. 레포의 그 파일을 읽고 현재 사이트 상태를 판단하면 **틀린 결론**이 나온다
2. `netlify.toml`의 조립 단계는 `if [ -f _parts/index.sha256 ]` 조건부다. 만약 조각이나 체크섬이
   사라지면 이 낡은 파일이 그대로 배포되어 **사이트가 조용히 8/11 이전으로 되돌아간다**

`_parts/README.md`에 경고와 확인 절차를 명시했다.

### 발견 ③: `.gitignore` 부재 — **조치함**

`public/rss.xml`·`public/build-index.sha256`이 빌드 생성물인데 무시 규칙이 없어
작업 때마다 미추적 파일로 뜸고, 실수로 커밋될 여지가 있었다. `.gitignore` 신설.

## 7. 운영 규칙에 반영할 항목 (본문 미수정)

`claude/세꼼이-운영-규칙.md`는 32KB이고 한글 밀도가 높다.
3절에서 실증된 전사 오류가 **운영 규칙 본문에 들어가면 자동화가 잘못된 규칙을 읽는다** —
CSS 주석 오타와는 위험도가 다르다. 그래서 이번 세션에서는 본문을 건드리지 않았다.

대신 기술 규칙은 `_parts/README.md`에 넣었다(작고 안전한 파일이며, `_parts`를 만지는
세션이 반드시 읽는 위치다). 아래는 운영 규칙에 옛길 항목이다.

1. **빌드 파이프라인 5단계** — `cat _parts` 조립 → `build-blog-featured` → `build-seo-meta` →
   `build-llms-txt` → `build-rss` → `build-landing`. 마지막이 8/13 신설.
2. **랜딩 하단 수정 위치** — `_parts/landing-below.html`. `index.html.part*`도 `public/index.html`도 아니다.
3. **`.lp-foot` 동기화 주의** — `build-landing.cjs`가 히어로 안 푸터를 들어내고
   `landing-below.html` 끝 푸터로 대체한다. 한쪽만 고치면 푸터가 사라지거나 중복된다.
4. **주입 단계는 체크섬 검증이 없다** — 앵커를 못 찾으면 조용히 통과한다.
   본체 랜딩 마크업을 고쳤다면 배포 후 실제 페이지에서 섹션 존재를 확인할 것.
5. **미결 2건 해소 처리** — 5절 발견 ④.
6. **대용량 한글 파일 푸시 원칙** — 40KB 넘는 한글 파일은 통째 재업로드하지 말 것.
   불가피하면 푸시 후 새 clone으로 sha256 대조하고, 스크립트류는 주석까지 ASCII로 작성한다.

## 8. 오너 확인 필요

- **PC 와이드 전환**과 **강남↔분당 탭 동작** 실물 확인. 코드 검증까지만 했고 렌더링은 못 봤다.
- **GTM(선택)** — 퍼널 이벤트 트리거 정규식 끝에 `|cta_click`을 붙이면 어느 CTA가 먹히는지 보인다.
  안 붙여도 `start_calc`은 정상 작동한다.
- **GTM(미결 유지)** — `calc_complete`의 `tax_total`·`case_id`·`region`, `scenario_open`의 `scenario` 등
  기존 이벤트 매개변수는 여전히 GA4로 안 간다. 8/11에 단계 계측 4줄만 추가했다.
  `GA4 퍼널` 태그에 매개변수 행을 더하고 데이터 영역 변수를 만들면 해소된다.
- **잔재 폴더 물리 삭제(선택)** — 5절 발견 ①. 서빙은 차단됐으니 급하지 않다.
